# 加密音频容器的原理与边界（研究笔记）

> 本文只讨论**原理与工程结构**，不提供任何密钥、算法参数或可运行代码。
> 目的：帮助理解"为什么本地格式转换是一个工程问题"，以及为什么它同时是一个法律问题。

## 1. 容器与编码不是一回事

一首歌通常由两层组成：

- **编码（codec）**：MP3、AAC、FLAC、Vorbis、Opus……决定声音怎么被压缩。
- **容器（container）**：MP3 帧、MP4 box、FLAC metadata block、Ogg page……决定数据怎么组织。

平台下载的"加密格式"通常是在**普通容器外面再套一层**：文件头被改写、字节流被变换、
密钥被包装在尾部的某个结构里。播放器需要先"拆壳"，才能拿到真正的 MP3/FLAC 流。

这也解释了为什么这类文件在普通播放器里打不开，但在平台客户端里能播——客户端知道怎么拆。

## 2. 常见的混淆手段（概念层）

不同平台的做法不同，但大体可以归为几类：

1. **头部混淆**：文件开头一段不是标准的 `fLaC` / `ID3` / `ftyp`，而是平台自定义的魔数。
   拆壳的第一步永远是识别魔数、定位真正的音频起点。
2. **字节流变换**：对音频数据做逐字节的可逆变换（异或、查表、流密码……）。
   变换通常与偏移量或密钥相关，因此不能简单地"从头解到尾"。
3. **密钥包装**：真正的密钥不以明文出现，而是经过一层或多层加密后放在文件尾部；
   客户端用内置的根密钥解开包装，再派生流密钥。
4. **元数据旁路**：歌名、歌手、封面、歌词可能放在壳的头部（而不是音频标签里），
   拆壳时要一起取出来，否则转换后就没有封面和歌词了。

这些设计的目标不是"强加密"，而是**提高批量处理的成本**：让通用工具难以直接读，
同时保证官方客户端能在各种设备上快速解密。

## 3. 为什么"完美兼容"很难

- **版本碎片化**：同一平台的不同版本、不同下载渠道，壳的布局可能不同（例如尾部密钥的
  大小端、是否带标签、是否分块加密）。
- **边界情况**：文件被截断、尾部被追加数据、密钥长度异常、音频格式与扩展名不一致……
  这些都需要兜底策略，否则就会"大部分能转，少数文件失败"。
- **元数据丢失**：壳里带的封面/歌词如果没解析出来，转出来的文件就没有封面——用户会
  觉得"转换失败"，其实是元数据没接上。

一个健壮的实现，工作量往往不在"解密"本身，而在**格式识别、边界处理、元数据迁移和
失败恢复**上。

## 4. 人声 / 伴奏分离是另一条技术线

"去掉人声留伴奏""只听鼓""只听钢琴"属于**音源分离（source separation）**，和容器解密无关：

- **中置消除**：人声通常位于声场中央，左右声道相减可以抵消中央成分。实现简单，
  但贝斯、底鼓会一起消失，残留明显。
- **谱分解 / 重复结构分析**：利用伴奏的重复性、人声的非重复性做掩码，属于传统 DSP。
- **深度学习**：用 U-Net / Transformer 类模型把混音拆成若干轨（人声、鼓、贝斯、吉他、
  钢琴、其他）。质量远好于中置消除，但需要模型推理，CPU 上每首歌要几十秒到几分钟。
- **主唱 vs 和声**：这是更难的问题，需要专门的"卡拉 OK"模型；通用分轨模型通常把
  主唱和和声放在同一条"人声"轨里。

## 5. 法律与伦理边界

这类工具处在灰色地带：

- 中国《著作权法》第 49 条、美国 DMCA §1201 都禁止"规避技术措施"，且针对的是
  **提供手段**，不只是自己使用。
- 同类开源项目（如 unlock-music）曾在 2022 年被 DMCA 投诉，GitHub 仓库被 451 封禁。
- "仅用于学习研究"的例外通常很窄，**公开发布可运行的解密工具**很难被归入其中。

因此本仓库的选择是：

- 只保留**不涉及解密**的转换、标签、封面、歌词、界面与打包部分；
- 把这部分做成一个干净、可复用的音频工具；
- 原理性研究以文档形式公开，不附带密钥或可运行实现。
